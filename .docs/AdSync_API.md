# AdSync_API — API fs-adsync и интеграция с сайтом (fs-lms)

Название файла — по аналогии с `VU_API.md` в репозитории `fs-video-uploader` (`AdSync` = имя модуля fs-lms, которому соответствует этот сервис). Здесь — обе стороны контракта:

1. **Входящий HTTP API** — то, что этот сервис предоставляет сам (для мониторинга/техперсонала).
2. **Исходящий REST** — то, чем сервис стучится в fs-lms, забирая задания и отчитываясь по ним.

Реализация: `src/api.py` (входящий API), `src/lms.py` (исходящий REST), нормативный источник контракта fs-lms — `.docs/FS_LMS_API.md`, раздел AdSync.

- Базовый URL входящего API: `http://<host>:<API_PORT>` (по умолчанию порт `8091`, см. `.env`; `8090` занят `fs-video-uploader` — не путать).
- Аутентификации на входящем API нет — доступ ограничен сетевым сегментом (Tech/Admin), не приложением. Входящих запросов от WP не существует в принципе — модель строго pull, WP никогда не стучится в этот сервис.
- Формат — везде `application/json`.
- Синхронные обработчики: FastAPI сам уводит их в threadpool (внутри — блокирующие вызовы к SQLite).

## 1. Входящий HTTP API (этот сервис)

### `GET /health`

Проверка живости процесса — используется Docker `HEALTHCHECK` в `docker-compose.yml`.

**Запрос**

```bash
curl -s http://localhost:8091/health
```

**Ответ `200 OK`**

Сразу после старта, до первого тика заданий/сверки:

```json
{
  "status": "ok",
  "last_jobs_poll_at": null,
  "last_reconcile_at": null
}
```

После хотя бы одного тика каждого цикла — ISO 8601, UTC:

```json
{
  "status": "ok",
  "last_jobs_poll_at": "2026-07-20T13:44:12.405483+00:00",
  "last_reconcile_at": "2026-07-20T10:00:03.100000+00:00"
}
```

`status` всегда `"ok"`, если процесс жив и ответил — эндпоинт не проверяет доступность LDAPS/WP отдельно, это было бы дороже, чем нужно для liveness-проверки контейнера. Диагностика конкретных проблем — `GET /status` и логи (Loki/`DATA_DIR/logs/adsync.log`).

### `GET /status`

Агрегаты по журналу обработок + последние записи — для быстрой диагностики без похода в SQLite напрямую.

**Запрос**

```bash
curl -s http://localhost:8091/status
```

**Ответ `200 OK`**

```json
{
  "done": 128,
  "failed": 3,
  "dead": 1,
  "recent": [
    {
      "job_id": 42,
      "idempotency_key": "app:17",
      "event": "provision",
      "username": "i.petrov",
      "subject_key": "inf-ege",
      "status": "done",
      "error": null,
      "received_at": "2026-07-20T13:44:05.100000+00:00",
      "acked_at": "2026-07-20T13:44:05.410000+00:00"
    },
    {
      "job_id": 41,
      "idempotency_key": "deprovision:app:9",
      "event": "deprovision",
      "username": "a.sidorov",
      "subject_key": null,
      "status": "failed",
      "error": "учётная запись вне управляемой зоны",
      "received_at": "2026-07-20T13:41:00.000000+00:00",
      "acked_at": "2026-07-20T13:41:00.320000+00:00"
    }
  ]
}
```

Поля:

| Поле | Тип | Описание |
|---|---|---|
| `done`, `failed` | `number` | Суммарные счётчики по **всему** журналу (append-only — повторная выдача одного и того же `idempotency_key` считается отдельной строкой). |
| `dead` | `number` | Количество **различных** `idempotency_key`, у которых подряд накопилось 6+ записей `status="failed"` — тот же порог, что определяет «мёртвое» задание в разделе 2. |
| `recent` | `array` | Последние 20 записей журнала, самые свежие первыми (`ORDER BY id DESC`). Каждый элемент — строка таблицы `jobs` (`JobRepository`), без пароля/сырого payload — их в схеме нет в принципе, фильтровать нечего. |
| `recent[].subject_key` | `string \| null` | Заполнено только у `provision`; `null` у `deprovision`. |
| `recent[].error` | `string \| null` | `null` при `status="done"`. |
| `recent[].received_at`, `.acked_at` | `string` | UTC, ISO 8601. |

Пустой журнал (сервис только что запущен) — `{"done": 0, "failed": 0, "dead": 0, "recent": []}`.

### `POST /reconcile`

Триггер внеочередного прогона сверки, не дожидаясь `RECONCILE_INTERVAL_HOURS`.

**Запрос**

```bash
curl -s -X POST http://localhost:8091/reconcile
```

Тело запроса не требуется и игнорируется.

**Ответ `200 OK`**

В отличие от `/rescan` у `fs-video-uploader`, здесь ответ **синхронный** — эндпоинт дожидается завершения прогона и возвращает его результат:

```json
{
  "aborted": false,
  "abort_reason": null,
  "disabled_usernames": ["a.sidorov"]
}
```

Если прогон отменён предохранителем (см. раздел 2, `GET /ad/active-usernames`):

```json
{
  "aborted": true,
  "abort_reason": "пустой список активных логинов от LMS при непустой управляемой зоне",
  "disabled_usernames": []
}
```

Ручной запуск и плановый фоновый прогон используют один и тот же `Reconciler` под общим `threading.Lock()` — конкурентный вызов `/reconcile` во время уже идущей плановой сверки просто дожидается своей очереди, а не запускает второй прогон параллельно (важно, т.к. одновременная работа с одним LDAP-соединением небезопасна).

## 2. Исходящий REST: цикл заданий и сверка с fs-lms

Сервис сам выступает клиентом REST API плагина fs-lms (`src/lms.py`) — это вызовы наружу из `poller.py`/`reconcile.py`, а не эндпоинты этого сервиса.

### Аутентификация — HMAC

Единая схема интеграций fs-lms (та же, что у `fs-video-uploader`, см. `VU_API.md`).

```
Headers:
  X-Fs-Timestamp: <unix-время, секунды>
  X-Fs-Signature: hex( hmac_sha256( "{timestamp}.{raw_body}", FS_LMS_AD_HMAC_SECRET ) )
```

- `raw_body` — для `GET`-запросов пустая строка (`""`); для `POST /ad/ack` — байты JSON-тела **ровно в том виде**, в каком отправлены (`model_dump_json(exclude_none=True)`, подпись считается по тем же байтам, что уходят в запрос).
- Плагин отвергает запрос (`401`), если `|now − timestamp| > 300` секунд (анти-replay) или подпись не сошлась → **часы LXC должны быть синхронизированы (NTP)**, тот же контракт, что у `fs-video-uploader`.
- Секрет: `FS_LMS_AD_HMAC_SECRET` этого сервиса = константа в `wp-config.php` плагина, генерируется кнопкой в админке fs-lms («Синхронизация с доменом (AD)»). Отдельный секрет от `fs-video-uploader` (`LMS_HMAC_SECRET`/`FS_LMS_VIDEO_HMAC_SECRET`) — общая **схема** подписи, но не общий секрет между сервисами.
- Реализация — только stdlib `time`/`hmac`/`hashlib` (`src/lms.py`), без сторонних крипто-библиотек.

### `GET /ad/jobs`

Забирает готовые к выполнению задания.

```
GET {LMS_BASE_URL}/ad/jobs?limit={JOBS_LIMIT}
```

`limit` — 1–200 (по умолчанию 50), совпадает с диапазоном, который принимает контракт fs-lms (`.docs/FS_LMS_API.md`, §3.1).

**Ответ `200`** (пример смешанного списка):

```json
{
  "jobs": [
    {
      "id": 7,
      "event": "provision",
      "idempotency_key": "app:5",
      "username": "i.petrov",
      "password": "СекретУченика",
      "first": "Иван",
      "last": "Петров",
      "subject_key": "inf-ege"
    },
    {
      "id": 8,
      "event": "deprovision",
      "idempotency_key": "deprovision:app:9",
      "username": "a.sidorov"
    }
  ]
}
```

| `event` | Поля | Действие в AD |
|---|---|---|
| `provision` | `username, password, first, last, subject_key` | Создать/реактивировать/обновить учётку в OU направления по `subjects.yaml` (см. `.docs/basic_doc.md`, раздел 4) |
| `deprovision` | `username` | Отключить учётку, перенести в `AD_OU_DISABLED` |

Задание может **исчезнуть** из следующей выдачи (заявку удалили на стороне WP) — это не ошибка, ack по нему не требуется и не отправляется.

> **О событии `promote`**: нормативный контракт fs-lms прямо говорит, что события `promote` **не
> существует** — учётка создаётся один раз сразу в целевой OU направления и остаётся там до
> отчисления, промежуточной стадии «зачислен» в OU-структуре нет (`.docs/FS_LMS_API.md`, §3.1;
> `.docs/AdSyncPythonService.md`, §3.1, тот же тезис дословно). Изначально в этом сервисе был
> реализован `PromoteJob`/`PromoteHandler` как задел на случай появления такого события в будущем —
> при сверке с нормативными документами модуля `Inc\Modules\AdSync` выяснилось, что WP никогда не
> шлёт `event: "promote"` и не планирует, и задел убран целиком (модель, обработчик, строка в
> реестре `main.py`, связанные тесты). Единственные два реальных события — `provision` и
> `deprovision`, ровно как в таблице выше.

### `POST /ad/ack`

Отчёт о выполнении одного задания — **обязателен на каждое обработанное задание**, и при успехе, и при ошибке.

```
POST {LMS_BASE_URL}/ad/ack
{"id": 7, "status": "done"}
```

или, при ошибке:

```json
{"id": 7, "status": "failed", "error": "учётная запись вне управляемой зоны"}
```

- Поле `sam_account_name`, которое контракт fs-lms допускает как опциональное (для аудита), этот сервис **никогда не отправляет** — WP его не использует, а лишнее поле в подписанном теле не даёт практической пользы. Осознанное решение, зафиксировано в `.docs/CLAUDE.md`.
- `error` отсутствует в JSON целиком при `status="done"` (`exclude_none=True`), не передаётся как `null`/`""`.

**Ответ `200`:** `{"ok": true}`.

### `GET /ad/active-usernames`

Авторитетный список логинов, которые должны оставаться активными — используется циклом сверки (`reconcile.py`).

```
GET {LMS_BASE_URL}/ad/active-usernames
```

**Ответ `200`:**

```json
{"usernames": ["i.petrov", "a.sidorov", "p.orlov"]}
```

Активная учётка управляемой зоны, чьего логина нет в этом списке → путь `deprovision` (отключить + перенести в `AD_OU_DISABLED`), с учётом grace-периода и предохранителей (см. `.docs/CLAUDE.md`, раздел «Сверка»).

### Обработка ошибок и ретраи

| Что происходит | Итог | Поведение |
|---|---|---|
| `GET /ad/jobs` — сеть/`5xx`/`4xx`/невалидный JSON | Тик пропущен | `logger.exception(...)` (ERROR), ack никому не шлётся, следующая попытка — на следующем тике (`JOBS_POLL_SECONDS`); локальных ретраев внутри одного тика нет |
| `POST /ad/ack` — сеть/`5xx`/`4xx` | Запись **не** попадает в журнал | ERROR в лог; WP не получил подтверждение → само задание естественно переотдастся на следующем опросе (штатный pull-ретрай, ничего специально не нужно) |
| Обработчик задания бросил исключение (LDAP-ошибка и т.п.) | `ack(failed, error=...)` | Ошибка одного задания не прерывает обработку остальных в этой же пачке |
| `status="failed"` шестой раз подряд по одному `idempotency_key` | «Мёртвое» задание | ERROR в лог (см. `.docs/basic_doc.md`, раздел 4, про канал оповещений); WP само перестаёт выдавать это задание после 6 неудач — фактическое поведение полностью определяет сторона WP, этот сервис только фиксирует факт |
| **Ретраи и backoff между тиками** — целиком на стороне WP (экспоненциальная задержка `next_attempt_at`); у клиента (`src/lms.py`) собственных ретраев нет — любая ошибка сразу пробрасывается вызывающему коду. |

## 3. Соответствие подходов с `fs-video-uploader`

Оба сервиса инфраструктуры сознательно построены на одной и той же модели наблюдаемости и интеграции:

| Аспект | fs-adsync | fs-video-uploader |
|---|---|---|
| HMAC-подпись исходящих запросов | `hex(hmac_sha256("{ts}.{raw_body}", secret))`, заголовки `X-Fs-Timestamp`/`X-Fs-Signature` | Идентичная формула и заголовки (`VU_API.md`, раздел 2) |
| Анти-replay окно | ±300 с, требует NTP на LXC | То же самое |
| Логирование | Единый канал — stdlib `logging` → file + Loki (`LOKI_URL`); Telegram/боты не встроены в код сервиса, оповещения — через Grafana Alerting поверх Loki | Тот же принцип: «Telegram-бот… читает события из Loki, а не получает push» (`basic_doc.md`, раздел 4) |
| Входящий HTTP API | `/health`, `/status`, без бизнес-логики | `/health`, `/status`, `/rescan`, без бизнес-логики |
| Секреты | Отдельный HMAC-секрет (`FS_LMS_AD_HMAC_SECRET`) на каждый модуль fs-lms, схема общая | Отдельный секрет (`LMS_HMAC_SECRET`) |

Одно осознанное отличие: `fs-video-uploader` держит `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` в `Settings` как задокументированную заглушку под тот же принцип «боты читают Loki» (файлы-заглушки `logging_setup/telegram.py`, `notifications/telegram.py`); в `fs-adsync` эти переменные и соответствующий код отсутствуют полностью — убраны в процессе разработки, когда было явно решено не встраивать прямой пуш в Telegram даже как задел. Функционально это не расхождение (ни один из сервисов не шлёт в Telegram напрямую), только разница в том, оставлен ли неиспользуемый параметр про запас.
