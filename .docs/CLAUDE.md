# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

`fs-adsync` — сервис, который создаёт и сопровождает доменные учётки учеников по заявкам из LMS (WordPress-плагин `fs-lms`, модуль `Inc\Modules\AdSync`).

Модель взаимодействия — **push** (с 2026-09, до этого был pull-поллер):

- Сайт сам присылает задания: подписанный HTTPS-запрос на белый IP офиса, роутер пробрасывает порт на контейнер. Сервис выполняет задание в Active Directory по LDAPS и **в том же ответе** возвращает результат — отдельного ack нет.
- Очередь, ретраи с бэкоффом и «мёртвые» задания — на стороне сайта (таблица `fs_lms_ad_outbox`). Сервис своих циклов опроса не имеет: пока офис недоступен, задания ждут на сайте.
- От заявки на сайте до входа ученика за компьютер — **секунды**: сайт шлёт задание сразу после отправки формы.
- Контракт (сеть, TLS, подпись, эндпоинты, коды ответа) нормативно описан в `.docs/AdSyncPythonService.md` — это копия документа из репозитория сайта, меняются синхронно. **Читается до написания любого кода.** Этот CLAUDE.md его не дублирует, а фиксирует принятые решения поверх.
- Жизненный цикл учётки упрощён относительно ТЗ (согласовано с администратором домена): OU `Pending`/`Active` **не используются** — `provision` кладёт ученика сразу в OU направления, где уже действуют существующие GPO. Отчисление = отключение учётки + перенос в OU «Отчисленные». Hard-delete запрещён всегда.

Два входа, оба — от сайта:

```
POST /v1/jobs       (сразу после события на сайте): подпись → обработчик → журнал → {status, error}
POST /v1/reconcile  (раз в сутки):  подпись → список «кто должен жить» → отключить лишних (с предохранителями)
GET  /v1/health     (кнопка «Проверить соединение»): подпись → пробный запрос к DC
```

- Python 3.12+, менеджер — **uv** (`pyproject.toml` + `uv.lock`, src-layout)
- pydantic v2 + pydantic-settings — `Settings`, валидация `subjects.yaml`, discriminated union заданий

- dev: pytest, ruff, mypy

Запрещено добавлять без явного запроса: APScheduler, EventBus-слой, DI-контейнеры, asyncio, requests, python-telegram-bot, cryptography, любой ORM.

## Code Style

- PEP 8 через `ruff format` + `ruff check`; line-length 100; конфиг в `pyproject.toml`
- `mypy --strict`; типы у всех параметров и возвращаемых значений
- ООП: логика в классах, зависимости — через конструктор; интерфейсы — `typing.Protocol`
- Внешние DTO и конфиги — pydantic; внутренние значения — frozen `dataclass(slots=True)` по необходимости
- Там, где логика зависит от времени (reconcile, grace-период), время передаётся зависимостью: `now: Callable[[], datetime]` в конструкторе — тестируется подстановкой, freezegun не нужен
- Пути — только `pathlib.Path`
- `print` запрещён — только `logging` (логгеры `adsync.<module>`)
- Docstrings (Google style) на публичных классах и методах
- Никакого глобального изменяемого состояния и синглтонов; вся сборка зависимостей — в composition root (`main.py`)

## SOLID в этом проекте

SOLID здесь — про границы, а не про количество паттернов:

- **S** — модуль отвечает за одно: `jobs.py` не знает про LDAP и HTTP, шлюз не знает про бизнес-правила, репозиторий не знает про ответ сайту.
- **O** — новый тип события от WP = новый класс-обработчик + строка в реестре-словаре в `main.py`; существующий код не правится.
- **L** — реализации Protocol полностью взаимозаменяемы (боевые классы и фейки в тестах).
- **I** — два узких Protocol: `JobHandler`, `DirectoryGateway`.
- **D** — ldap3 / sqlite3 живут только внутри `ad.py` / `repository.py`, httpx — только в лог-хендлерах `logging_setup.py`, FastAPI — только в `api.py`; остальной код зависит от Protocol и вызываемых объектов; конкретика подключается в `main.py`.

Сознательно **не** вводим: EventBus и отдельный слой бизнес-уведомлений (вместо них — единый канал `logging`, а мессенджер-алертинг, если понадобится, настраивается поверх Loki в Grafana Alerting, не в коде сервиса), APScheduler (два daemon-потока `while not stop.wait(interval)`), вложенные пакеты (модули плоские — семейств стратегий здесь нет), use-case-слои, иерархии собственных исключений (собственных исключений всего несколько, все —
плоские, без базового класса и наследников: `OutsideManagedZoneError`, `ManagedZoneConfigError`
и `CnAllocationError` в `ad.py` — guard зоны, проверка конфигурации на старте и исчерпание
вариантов CN в целевой OU; `DirectoryUnavailableError` в `ad.py` — DC недоступен и после
переподключения, API отвечает сайту `503`; `SignatureRejectedError` в `api.py` — ответ `401`).

## Architecture

| Модуль (`src/adsync/`) | Роль |
|---|---|
| `main.py` | Composition root: `Settings` → сборка зависимостей → реестр обработчиков (обычный dict `{"provision": …}`) → два uvicorn (публичный TLS + локальный) + heartbeat/сводка; graceful shutdown по SIGTERM |
| `config.py` | `Settings` (pydantic-settings) + загрузка и валидация `subjects.yaml` |
| `models.py` | `ProvisionJob \| DeprovisionJob` — discriminated union по полю `event`; ответ на задание; запрос/ответ сверки |
| `auth.py` | `SignatureVerifier`: подпись запросов сайта (stdlib `hmac`), окно по времени |
| `ad.py` | `DirectoryGateway` (Protocol) + `AdGateway` (ldap3): идемпотентные операции, контроль управляемой зоны, переподключение при обрыве, `DirectoryUnavailableError` |
| `handlers.py` | `JobHandler` (Protocol) + `ProvisionHandler` / `DeprovisionHandler` |
| `jobs.py` | `JobProcessor`: одно задание → обработчик → журнал → итог; строго по одному (блокировка) |
| `reconcile.py` | Сверка: список от сайта против активных учёток зоны; предохранители; режим «только журнал» |
| `repository.py` | SQLite-журнал (append-only), dead-счётчик; ни пароля, ни сырых payload |
| `logging_setup.py` | Хендлеры file / loki + redaction-фильтр пароля — единственный канал уведомлений; мессенджер-алертинг (если понадобится) — поверх Loki в Grafana |
| `api.py` | FastAPI: публичный (`/v1/jobs`, `/v1/reconcile`, `/v1/health`, подпись обязательна) и локальный (`/health`, `/status`) — без бизнес-логики |

### Design Patterns

- **Strategy** — обработчики заданий за `JobHandler`; реестр — обычный dict в `main.py`, без фабрик-фреймворков и регистраций через декораторы.
- **Adapter/Gateway** — `LmsClient` (httpx), `AdGateway` (ldap3).
- **Repository** — `repository.py`, единственная точка доступа к SQLite.

Очередь и ретраи живут на сайте — не заводить здесь собственную очередь, планировщик или повторные попытки: сервис отвечает на запрос сайта и забывает о нём (кроме журнала).

## Contracts

### Публичный API (сайт → сервис; нормативный источник — `.docs/AdSyncPythonService.md`)

- Адрес: `https://<белый IP офиса>:{PUBLIC_PORT}`; сертификат самоподписанный, с IP в SAN (`config/tls/`); сайт доверяет только ему. На роутере порт открыт только для исходящего IP сайта.
- Подпись **каждого** запроса: `X-Fs-Timestamp` + `X-Fs-Signature = hex(hmac_sha256(METHOD + "\n" + PATH + "\n" + TIMESTAMP + "\n" + BODY))`, секрет `FS_LMS_AD_HMAC_SECRET` (тот же, что в `wp-config.php`; генерируется в админке сайта). Окно — `HMAC_MAX_SKEW_SECONDS`. Не прошла — `401`, запрос не обрабатывается.
- `POST /v1/jobs` — одно задание, ответ синхронный: `200 {status: done|failed, error}`. Невалидное тело — `422`. DC недоступен — `503` (**не ошибка задания**: сайт ставит доставку на паузу и попытку не тратит). Значит: ошибка данных/зоны — `failed`, временная проблема AD — только `DirectoryUnavailableError` → `503`, не путать.
- `POST /v1/reconcile` — `{usernames, apply}` → `{status: ok|aborted, applied, disabled, abort_reason}`.
- `GET /v1/health` — пробный запрос к DC: `200 {status, ldap}` или `503`.
- **Ретраи и backoff — целиком на стороне сайта**: наш `failed` ⇒ сайт повторит задание с экспоненциальной задержкой (1м → … → 1ч), после 6 неудач задание у сайта «мёртвое». Локальных ретраев нет.

### События → действия в AD

| `event` | payload | Действие |
|---|---|---|
| `provision` | `id, event, idempotency_key, username, password, first, last, subject_key` | Создать учётку в OU направления по `subjects.yaml`: `objectClass=user`, `sAMAccountName=username`, `userPrincipalName={username}@{AD_UPN_SUFFIX}`, `cn`/`displayName` из `first`+`last`; создаётся **отключённой** (`userAccountControl=514`) — AD отклоняет `add()` сразу включённой учётки без пароля (`WILL_NOT_PERFORM`/5003); пароль `unicodePwd` только по LDAPS через `extend.microsoft.modify_password`, и только **после** этого — включение (`userAccountControl=512`); `MODIFY_ADD` в security-группу направления |
| `deprovision` | `id, event, idempotency_key, username` | `userAccountControl=514` + `modify_dn` в `AD_OU_DISABLED` |
| `password` | `id, event, idempotency_key, username, password` | пароль через `ensure_password`; учётку не включает и не переносит (в «Отчисленных» остаётся отключённой) |

Когда какое событие приходит, решает сайт (таблица — `.docs/AdSyncPythonService.md` §4.1): `provision` —
заявка подана или ученик **повторно зачислен**, пока учётка в «Отчисленных» (это реактивация — ветка
«в `AD_OU_DISABLED`» ниже); `deprovision` — заявка истекла/удалена или ученик отчислен без других
действующих зачислений; `password` — администратор сменил пароль на сайте.

Никакой промежуточной стадии «зачислен» в OU-структуре нет: учётка создаётся
один раз сразу в целевой OU направления и остаётся там до отчисления. Событие `promote` в контракте
fs-lms не существует (см. `.docs/FS_LMS_API.md`, §3.1, и `.docs/AdSyncPythonService.md`, §3.1) — в
этом сервисе такой обработчик когда-то был реализован как задел, но убран при сверке с нормативными
документами модуля `Inc\Modules\AdSync`.

Правила поверх таблицы:

- **Незнакомый `subject_key`**: создать учётку в `AD_OU_FALLBACK` без группы направления → `done` + WARNING в лог. Не падать — ученик должен войти немедленно, маппинг админ дополнит потом.
- **provision, а учётка уже существует**: в OU управляемой зоны → ensure (пароль из payload + включена + членство в группе — включение обязательно и здесь, не только при создании: если предыдущая попытка упала между паролем и включением, повторная выдача не должна оставить учётку висеть отключённой навсегда) → `done`; в `AD_OU_DISABLED` → **реактивация** (включить, перенести в OU направления по `subject_key`, пароль, группа) → `done`; **вне управляемой зоны → `failed` + ERROR, объект не трогать** — это чужая учётка.
- **deprovision**: учётки нет → `done` (цель достигнута); уже отключена → `done`; вне зоны → `failed` + ERROR.
- **password**: учётки нет → `failed` + ERROR (`password_account_missing`: цель не достигнута, учётка пропала из домена); вне зоны → `failed` + ERROR; иначе пароль → `done` + INFO (`password_changed`). Пароль в логи не попадает.
- Обработчики **идемпотентны**: повторная присылка задания (ответ не дошёл до сайта, ретрай после `failed`, падение посреди обработки) переносится спокойно; «уже существует» / «уже в группе» / «уже отключена» — успех, не ошибка.
- **Тёзки получают разные учётки.** `CN` уникален только внутри своей OU, `sAMAccountName` — во всём домене, поэтому `entryAlreadyExists` при `add()`/`modify_dn` значит одно из двух: либо это наша же учётка с прошлой попытки (сверяем `sAMAccountName` по этому DN — совпал, значит повтор задания, успех), либо это ДРУГОЙ человек с тем же ФИО. Во втором случае продолжать работу с чужим DN нельзя (иначе тёзка получит сброс пароля на чужой учётке): `ad.py` подбирает следующий вариант `CN` — «Имя Фамилия (логин)» — и логирует `cn_collision` (WARNING). `displayName` при этом у обоих остаётся человеческим. Исчерпание вариантов (`_MAX_CN_CANDIDATES`) → `CnAllocationError` → `failed`, объект не тронут.
- `idempotency_key` — ключ журнала и dead-счётчика, **не барьер и не кэш ответа**: при повторной присылке работа выполняется заново (идемпотентно) и ответ считается заново.
- **Dead**: наш 6-й `failed` по одному `idempotency_key` ⇒ ERROR в лог (`job_dead`). Сайт показывает «мёртвые» у себя в настройках модуля, но в Loki тревогу поднимает этот сервис.
- Успешные действия (создание учётки, реактивация, `deprovision` → `done`) логируются на уровне INFO — единый аудиторский след в логах, отдельного канала бизнес-событий нет.

### Сверка (reconcile)

- Управляемая зона: все `ou_dn` из `subjects.yaml` + `AD_OU_FALLBACK`. `AD_OU_DISABLED` — вне сверки.
- Активная учётка зоны, чьего `sAMAccountName` нет в списке от WP → путь deprovision (отключить + перенести в «Отчисленные»).
- **Предохранители** — нарушение любого ⇒ ничего не отключать, ERROR в лог:
  - пустой список при непустой зоне — abort всегда;
  - к отключению больше `RECONCILE_MAX_DISABLE` учёток — abort;
  - к отключению больше `RECONCILE_MAX_DISABLE_PCT`% зоны — abort.
- Сверку запускает сайт (`POST /v1/reconcile`, раз в сутки и вручную `wp fs-lms ad reconcile`); своего расписания у сервиса нет.
- `apply: false` — режим «только журнал»: предохранители проверяются так же, лишние учётки перечисляются в логе (`reconcile_dry_run`) и в ответе, AD не меняется. Так сверка работает первую неделю, потом на сайте включают отключение.
- Grace: учётки с `whenCreated` моложе `RECONCILE_GRACE_MINUTES` не трогаются (гонка со свежим provision против чуть устаревшего списка).
- Сверка **односторонняя**: никого не включает, не создаёт и не переносит обратно.
- Успешный прогон без abort логируется на уровне INFO (сколько отключено, если есть).

### config/subjects.yaml

```yaml
subjects:
  inf-ege:                      # subject_key из WP (стабильный слаг направления)
    ou_dn: "OU=КЕГЭ,OU=Ученики,OU=Пользователи,OU=LocalOffice,DC=fs,DC=loc"
    group_dn: "CN=KEGE,OU=Группы,OU=LocalOffice,DC=fs,DC=loc"
```

- Ключ — `subject_key`; DN в примере иллюстративные, реальные подставляются при деплое.
- Разные ключи могут вести в одну OU/группу — это допустимо.
- Валидация pydantic на старте (непустые DN, корректная схема); ошибка → падение на старте с внятным сообщением.
- Дополнительно на старте `AdGateway` проверяет существование в AD каждого `ou_dn`/`group_dn` из карты, а также `AD_OU_DISABLED` и `AD_OU_FALLBACK`; любой отсутствующий DN → падение на старте с внятным сообщением (fail fast: опечатка в DN не должна всплывать на первом задании).

## Job Processing Rules

- Одно задание — один запрос сайта. FastAPI выполняет запросы в пуле потоков, но задания обрабатываются строго по одному (блокировка в `JobProcessor`: одно LDAP-соединение). После простоя офиса сайт присылает хвост очереди подряд — штатная ситуация.
- Ошибка задания (зона, CN, LDAP-операция) → `failed` с `error`; процесс не падает. Недоступность DC (`DirectoryUnavailableError`) — не ошибка задания: в журнал не пишется, ответ `503`.
- Тело запроса валидируется pydantic на входе; невалидное задание → `422` + ERROR (`job_invalid`), без попытки обработки.
- **Пароль живёт только в памяти** на время запроса; не попадает в журнал, логи, уведомления и `/status` (redaction-фильтр — страховка, а не разрешение).
- SIGTERM: uvicorn дообрабатывает текущие запросы и новых не принимает; затем корректно закрываются LDAP-соединения и журнал.

## State (SQLite)

- Файл `DATA_DIR/state.db`; режим WAL; доступ — только через `repository.py`; без ORM.
- Таблица `jobs` — append-only журнал обработок: `id`, `job_id`, `idempotency_key`, `event`, `username`, `subject_key` (NULL для `deprovision`), `status` (`done`|`failed`), `error` (NULL), `received_at`, `acked_at` (момент ответа сайту; имя колонки — со времён pull и ack, не переименовываем ради живых `state.db`). **Пароль и сырой payload не сохраняются никогда.**
- Dead-счётчик = `COUNT(status='failed')` по `idempotency_key`; отдельной машины состояний нет — журнал фактов.
- Времена в БД — UTC ISO 8601.

## Logging & Notifications

Единый канал: всё, что происходит в сервисе — успешные операции, предупреждения, ошибки —
проходит через стандартный `logging`. Отдельного слоя бизнес-уведомлений в коде сервиса нет.
Оба сервиса инфраструктуры (этот и fs-video-uploader) пишут в общий Loki; если понадобится
оповещение в мессенджер — это Grafana Alerting поверх Loki (LogQL-правило + contact point),
настраивается руками в Grafana, не в этом репозитории.

- Только stdlib `logging`; хендлеры собирает `logging_setup.py`:
  - file — `RotatingFileHandler` `DATA_DIR/logs/adsync.log` (10 MiB × 5), всегда включён;
  - loki — HTTP push (`/loki/api/v1/push`) при заданном `LOKI_URL`. **Loki общий для всей инфраструктуры** (тот же контейнер, что у fs-video-uploader); лейблы потока — `service="fs-adsync"`, `level`, и опционально `event` (см. ниже). `username`/`idempotency_key`/числовые агрегаты — по-прежнему только в тексте строки, не в лейблах — это лейблы высокой кардинальности, Loki их не любит.
  - **`event`-лейбл** (2026-07-22, синхронизировано с решением в fs-video-uploader — см. его `CLAUDE.md`, тот же раздел): на значимых бизнес-событиях и основных инфраструктурных логах передаётся `extra={"event": "..."}`; `LokiHandler.emit` добавляет его третьим лейблом, только если он есть у записи (обычные логи без `extra` лейбла не получают). Кардинальность фиксированная — около 25 значений (полный список с уровнями и файлами — `.docs/basic_doc.md`, раздел «Метрики и алерты в Grafana»). Единого словаря имён в коде нет: каждое имя — литеральная строка по месту вызова (столько мест не сочли поводом для отдельной абстракции — то же решение, что в fs-video-uploader); опечатка/рассинхрон строк ловится тестами, не типами.
- **Старт/стоп**: `fs-adsync запускается` (`main.py`, сразу после `configure_logging`) / `fs-adsync
  остановлен` (в конце `main()`, после закрытия всех клиентов) — единообразно с fs-video-uploader.
- **Heartbeat**: раз в `HEARTBEAT_INTERVAL_SECONDS` (default `3600`) — `fs-adsync жив: done=N,
  failed=N, dead=N` (сводка `JobRepository.status_counts()`), отдельный демон-поток `heartbeat` по
  тому же идиому `_loop()`, что у `jobs`/`reconcile` (первый heartbeat ждёт полный интервал, как и
  первый тик остальных циклов — не срабатывает мгновенно при старте). Не привязан к
  `JOBS_POLL_SECONDS` намеренно — по этой же причине из него в своё время убрали лог числа заданий
  за тик (шумит на каждые 3 секунды даже без единого задания); heartbeat — редкий и всегда содержит
  осмысленные агрегаты, а не «X заданий, ноль».
- **Redaction-фильтр** (`logging.Filter`): значения полей `password`/`unicodePwd` вырезаются из любых записей до форматирования.
- Уровни осознанно расставлены по всему коду:
  - INFO — успешные операции: создание/реактивация учётки, `deprovision` → `done`,
    успешный прогон сверки (сколько отключено, если есть);
  - WARNING — некритичные аномалии, не требующие немедленной реакции: незнакомый `subject_key`;
    запрос с неверной/просроченной подписью (`signature_rejected` — если повторяется, проверить
    секрет и часы); переподключение к AD (`ad_reconnect`);
  - ERROR — требует внимания: учётка/операция вне управляемой зоны, dead-задание (6-я подряд
    неудача по `idempotency_key`), abort сверки любым предохранителем, DC недоступен
    (`ad_unavailable`), невалидное задание от сайта (`job_invalid`). Именно
    по `level="error"` в Loki будет строиться Grafana-алерт, если/когда его настроят.
- Дневная сводка (создано/отключено/ошибок за сутки; время `DAILY_SUMMARY_TIME`, пусто =
  выключено) — отдельный INFO-лог с агрегатами из `JobRepository.daily_counts(...)`, считается и
  пишется в `main.py`; уровень INFO — под Grafana-алерт по `level="error"` не подпадает, это
  плановый отчёт для file/Loki, не тревога.

## HTTP API

- **Публичный** (`PUBLIC_PORT`, TLS, подпись обязательна): `POST /v1/jobs`, `POST /v1/reconcile`, `GET /v1/health` — контракт с сайтом, см. раздел Contracts. Документация FastAPI (`/docs`, `/openapi.json`) на нём выключена.
- **Локальный** (`API_PORT`, HTTP, без аутентификации — наружу не пробрасывается): `GET /health` → `{"status": "ok", "last_job_at": …, "last_reconcile_at": …}` для Docker HEALTHCHECK; `GET /status` → счётчики (done/failed/dead) + последние 20 записей журнала (без чувствительных полей).
- Бизнес-логики в `api.py` нет: проверка подписи, разбор тела и делегирование вызываемым объектам из `main.py`.

## Strict Rules

- pip запрещён; зависимости — только через `uv add` и только по согласованию.
- **Пароль из payload никогда не логируется и не сохраняется** — ни в SQLite, ни в файлы, ни в уведомления, ни в `/status`; живёт в памяти только на время запроса сайта. Redaction-фильтр обязателен.
- ldap3 / sqlite3 / FastAPI — только внутри `ad.py` / `repository.py` / `api.py`, httpx — только в лог-хендлерах `logging_setup.py`; остальной код работает через Protocol.
- **Управляемая зона** = OU из `subjects.yaml` + `AD_OU_FALLBACK` + `AD_OU_DISABLED`. Объекты вне зоны сервис не читает и не изменяет; попытка операции над чужой учёткой → `failed` + ERROR.
- Hard-delete объектов AD запрещён всегда и везде.
- Сверка не может отключить больше порогов из конфига; пустой список при непустой зоне — всегда abort; сверка никого не включает.
- Ответ на задание — строго `done`/`failed`; недоступность DC — только `503`, не `failed`.
- Обработчики идемпотентны; повторная выдача задания — штатная ситуация, не ошибка.
- Публичный API принимает только подписанные запросы сайта; новых эндпоинтов без подписи на нём не заводить. Локальный API наружу не пробрасывается.
- `print` запрещён; исключения не глотаются молча (минимум — лог с traceback).
- Не вводить EventBus, APScheduler, ORM, DI-контейнеры, asyncio, новые слои и зависимости без явного запроса.
- Работать поэтапно (план — в стартовом промпте): в конце этапа прогнать ruff + mypy + pytest и остановиться до подтверждения пользователя.
