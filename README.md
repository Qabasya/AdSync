Сервис, который создаёт и сопровождает доменные учётные записи учеников в Active Directory по заявкам из LMS (WordPress-плагин [fs-lms](https://github.com/Qabasya/fs-lms), модуль `AdSync`).

## Модель работы

**Push**: сайт сам присылает задания на белый IP офиса, роутер пробрасывает порт на контейнер.
Сервис выполняет задание в AD по LDAPS и в том же ответе возвращает результат.

```
Сайт (WP) ──HTTPS POST──▶ белый IP офиса :8443 ──проброс──▶ fs-adsync ──LDAPS──▶ контроллер домена
```

| Эндпоинт (публичный, TLS, подпись обязательна) | Кто вызывает | Что делает |
|---|---|---|
| `POST /v1/jobs` | сайт, сразу после события (заявка, отчисление) | операции в AD → запись в журнал → `{status: done\|failed}` |
| `POST /v1/reconcile` | сайт, раз в сутки | отключить в зоне тех, кого нет в присланном списке (или только журнал) |
| `GET /v1/health` | кнопка «Проверить соединение» на сайте | пробный запрос к DC |

Нормативный контракт (сеть, TLS, подпись, коды ответа) — `.docs/AdSyncPythonService.md`.

Ключевые инварианты:

- **Очередь и ретраи — на стороне сайта, не здесь.** На `failed` сайт сам повторяет задание с
  бэкоффом (1м → 2м → 4м → … → 1ч), после 6 попыток помечает `dead`. Сервис своих очередей и
  ретраев не держит — только логирует `job_dead`. Пока офис недоступен, задания ждут на сайте.
- **`503` — не ошибка задания.** Если контроллер домена недоступен и после переподключения,
  сервис отвечает `503`: сайт ставит доставку на паузу и попытку задания не тратит.
- **Guard управляемой зоны.** Зона — это OU направлений из `subjects.yaml` + `AD_OU_FALLBACK` +
  `AD_OU_DISABLED`. Любую операцию над объектом вне зоны сервис отклоняет (`zone_violation`), объект
  не трогает, задание получает `failed`. Так учётка преподавателя или админа не может быть
  задета совпадением логина.
- **Пароль устанавливается только по LDAPS.** Учётка создаётся отключённой (AD отклоняет создание
  включённой учётки без пароля — `WILL_NOT_PERFORM/5003`), затем пароль, затем включение.
- **Только подписанные запросы.** Каждый запрос сайта подписан HMAC (метод + путь + время + тело);
  неверная или просроченная подпись — `401`. На роутере порт открыт только для IP сайта.

## Что он делает

1. Принимает от сайта задания — `provision` (создать учётку по заявке или вернуть из «Отчисленных» при повторном зачислении), `deprovision` (отключить при отчислении без других действующих зачислений) или `password` (администратор сменил пароль на сайте); промежуточной стадии «зачислен» в OU-структуре нет. Когда что присылать, решает сайт.
2. Выполняет задание в Active Directory по LDAPS: новую учётку — сразу в OU направления по `subjects.yaml`, с паролем и членством в security-группе; при повторной присылке — идемпотентно (уже существует/уже в группе — не ошибка).
3. Незнакомый `subject_key` не роняет обработку — учётка создаётся в OU «Без направления», в лог уходит WARNING, маппинг администратор дополняет позже.
4. Отвечает сайту итогом (`done`/`failed`) синхронно; после 6 неудач подряд по одному заданию оно считается «мёртвым», сигнал — ERROR в лог.
5. Раз в сутки получает от сайта список активных логинов и сверяет его с реальными учётками управляемой зоны в AD: отключает лишних — с предохранителями (порог по количеству/проценту, grace-период для свежих учёток, отмена при пустом списке). Первую неделю — режим «только журнал» (переключается в настройках модуля на сайте).
6. Hard-delete учёток запрещён всегда — только отключение и перенос в OU «Отчисленные».

Всё состояние (что обработано, с каким статусом, сколько раз подряд падало) — в SQLite, append-only журнал, доступно через локальный HTTP `/status`.

## Установка и запуск локально

Нужен [uv](https://docs.astral.sh/uv/).

```bash
uv sync
cp .env.example .env                                    # секрет подписи, AD-реквизиты, пути TLS
cp config/subjects.yaml.example config/subjects.yaml     # прописать свои направления
uv run python src/main.py
```

Сервис поднимет публичный API на `PUBLIC_PORT` (TLS, по умолчанию 8443) и локальный — на
`API_PORT` (по умолчанию 8091). Без файлов сертификата (`TLS_CERT_FILE`, `TLS_KEY_FILE`) не стартует.

## Подключение к сайту (WordPress)

Со стороны сайта (модуль `AdSync` плагина [fs-lms](https://github.com/Qabasya/fs-lms)):

1. Модуль включён — тумблер на дашборде модулей или `define('FS_LMS_AD_SYNC', true);` в `wp-config.php`.
2. `define('FS_LMS_AD_HMAC_SECRET', '...');` в `wp-config.php` — значение генерируется кнопкой в
   админке секции «Синхронизация с доменом (AD)», это единственный источник истины. Ровно оно же
   идёт в `.env` сервиса.
3. `server.crt` сервиса (без ключа!) лежит на хостинге выше `public_html`, путь — в
   `define('FS_LMS_AD_SERVER_CERT', '...');`. Сайт доверяет только этому сертификату.
4. В настройках модуля — адрес сервиса `https://<белый IP офиса>:8443`, затем «Проверить соединение».
5. Сверить слаги направлений (`subject_key`), которые сайт реально присылает, со своим
   `subjects.yaml`. Незнакомый слаг обработку не роняет, но учётка уйдёт в `AD_OU_FALLBACK` без
   членства в группе направления.

Со стороны офиса:

1. **Сертификат** с белым IP офиса в SAN (срок 10 лет), в `config/tls/`:
   ```bash
   mkdir -p config/tls && cd config/tls
   openssl req -x509 -newkey rsa:3072 -sha256 -days 3650 -nodes \
     -keyout server.key -out server.crt -subj "/CN=adsync-office" \
     -addext "subjectAltName=IP:92.101.127.156" -addext "basicConstraints=critical,CA:TRUE"
   chown 1000:1000 server.key && chmod 600 server.key   # читает только пользователь контейнера
   ```
2. **Роутер**: проброс внешнего `8443` на контейнер `:8443`; в межсетевом экране — разрешить только
   исходящий IP сайта, остальным запретить. Проверять снаружи (с хостинга по SSH:
   `curl --cacert adsync-server.crt https://<IP>:8443/v1/health` → `401` без подписи — значит,
   TLS и порт в порядке).
3. **Время**: часы хоста синхронизированы (chrony) — подпись привязана ко времени.

При переезде сайта меняются только `FS_LMS_AD_HMAC_SECRET` (если выпущен новый) и правило на
роутере (исходящий IP нового хостинга).

## Настройка

Всё через переменные окружения / `.env` (см. `.env.example` — там расписана каждая переменная). Ключевое:

- **`FS_LMS_AD_HMAC_SECRET`** — секрет проверки подписи запросов сайта (совпадает с `wp-config.php` плагина); **`HMAC_MAX_SKEW_SECONDS`** — окно по времени.
- **`PUBLIC_PORT` / `TLS_CERT_FILE` / `TLS_KEY_FILE`** — публичный API для сайта и его сертификат.
- **`LDAP_HOST` / `LDAP_BIND_DN` / `LDAP_BIND_PASSWORD` / `LDAP_CA_CERT`** — доступ к домен-контроллеру по LDAPS (сертификат обязателен, отключать проверку нельзя).
- **`SUBJECTS_FILE`** — `subjects.yaml`, маппинг «направление → OU + группа в AD» (пример в `config/subjects.yaml.example`). `subject_key`, которого нет в файле, не роняет обработку — уйдёт в fallback-OU.
- **`AD_OU_DISABLED` / `AD_OU_FALLBACK`** — DN OU «Отчисленные» и «Без направления».
- **`RECONCILE_MAX_DISABLE` / `RECONCILE_MAX_DISABLE_PCT` / `RECONCILE_GRACE_MINUTES`** — предохранители сверки (режим «только журнал» / «отключать» выбирается на сайте).
- **`LOKI_URL`** — если задан, логи параллельно улетают в Grafana Loki. Это основной канал наблюдаемости — телеграм-уведомлений сервис сам не шлёт, для этого будет Grafana Alerting поверх Loki (как и у `fs-video-uploader`).

Обязательные поля (без них сервис не стартует — упадёт сразу с понятной ошибкой, а не по пути): `FS_LMS_AD_HMAC_SECRET` (непустой), `LDAP_BIND_DN`, `LDAP_BIND_PASSWORD`, `AD_OU_DISABLED`, `AD_OU_FALLBACK`, а также файлы `TLS_CERT_FILE` / `TLS_KEY_FILE`.

## Требования к домену (Active Directory)

Разовая настройка на стороне AD-администратора — код этого за собой не делает и без этого не
стартует:

1. **LDAPS на порту 636** с валидным сертификатом DC; корневой сертификат CA выкладывается в
   `config/ldap-ca.pem` (путь — `LDAP_CA_CERT`). Верификация включена жёстко (`CERT_REQUIRED`),
   отключить её нельзя: без LDAPS Active Directory не примет запись `unicodePwd`.
2. **OU-структура заведена заранее** — по одной OU на направление + OU «Отчисленные»
   (`AD_OU_DISABLED`) + OU «Без направления» (`AD_OU_FALLBACK`). На старте сервис проверяет
   существование всех DN из конфигурации и падает с понятным сообщением, если хоть одного нет.
3. **Security-группы направлений** (`group_dn` в `subjects.yaml`) — их DN проверяются на старте
   вместе с OU.
4. **Сервис-аккаунт наименьших прав** (`LDAP_BIND_DN`) с делегированием на управляемые OU: создание,
   изменение и перемещение объектов между ними + запись `unicodePwd`. За пределы зоны сервис не
   ходит сам, но и прав туда давать не нужно.
5. **Fine-Grained Password Policy** на OU учеников с ослабленной сложностью и минимальной длиной.
   Иначе AD отклонит простой пароль, заданный учеником в форме на сайте, и `provision` будет
   стабильно получать `failed` до статуса `dead` — WP пароль не валидирует и политику домена
   не знает.
6. Права на общие ресурсы, ярлыки, раскладку меню и т. п. — через GPO/ACL **по OU направления**. К
   рантайму сервиса это не относится: он только размещает учётку в нужной OU, остальное отрабатывают
   уже существующие политики.

## Логины и совпадения имён

Логин (`sAMAccountName`) приходит готовым из WP — **сервис его не генерирует и уникальность не
обеспечивает**. Дедупликация внутри сервиса относится к *заданиям*, а не к людям: ключ
`idempotency_key` (`app:5`, `deprovision:person:3`) плюс append-only журнал в SQLite — по ним
считается число неудачных попыток подряд и ведётся аудит.

Поиск существующей учётки идёт по `sAMAccountName` от корня домена, а не только по управляемой зоне.
Поведение при совпадении логина:

| Где нашлась учётка | Что делает сервис |
|---|---|
| OU «Отчисленные» | реактивация: включить → перенести в OU направления → задать новый пароль → в группу (`account_reactivated`) |
| Живая, внутри зоны | считает, что это тот же человек: сбрасывает пароль на новый, включает, добавляет в группу (`account_updated`) |
| Вне управляемой зоны | объект не тронут, `zone_violation`, `failed` → после 6 попыток `dead` |

Отсюда следствие, которое стоит держать в голове: если WP выдаст **уже занятый** живой логин другому
ученику, сервис их не различит — новый ученик получит доступ к чужой учётке, а прежний владелец
потеряет пароль. Уникальность логинов обязана обеспечиваться на стороне WP при их генерации, там для
этого есть база всех учеников.

А вот **совпадение ФИО при разных логинах учёток не путает**. `CN` уникален только внутри своей
OU, поэтому второй «Иван Петров» в том же направлении получает собственный объект под
`CN=Иван Петров (i.petrov2)` — сервис сверяет `sAMAccountName` по занятому DN и, убедившись, что
это другой человек, подбирает следующий вариант CN (в лог уходит WARNING `cn_collision`).
`displayName` у обоих остаётся человеческим, в консоли AD они различимы по логину в скобках. То же
касается переноса между OU при реактивации.

Сверка сопоставляет учётки со списком от сайта тоже **только по логину** — ФИО, дата создания
(кроме grace-периода) и членство в группах не учитываются.

## HTTP API

Публичный (TLS, `PUBLIC_PORT`, только подписанные запросы сайта):

- `POST /v1/jobs` — одно задание; `200 {status, error}`, `422` невалидное тело, `503` DC недоступен.
- `POST /v1/reconcile` — сверка по списку от сайта; `{status: ok|aborted, applied, disabled, abort_reason}`.
- `GET /v1/health` — пробный запрос к DC; `200` или `503`.

Локальный (HTTP, `API_PORT`, наружу не пробрасывается):

- `GET /health` — жив ли процесс, время последнего задания и сверки (Docker HEALTHCHECK).
- `GET /status` — счётчики (`done`/`failed`/`dead`) + последние 20 записей журнала.

Подробнее с примерами запросов/ответов — в `.docs/AdSync_API.md`, нормативный контракт — в
`.docs/AdSyncPythonService.md`.

## Деплой (Docker)

```bash
cp .env.example .env
cp config/subjects.yaml.example config/subjects.yaml
docker compose up -d --build
```

Ожидаемая раскладка файлов рядом с `docker-compose.yml`:

```
.
├── .env                 # именно .env — compose читает его через env_file
├── docker-compose.yml
├── config/              # монтируется как /app/config:ro
│   ├── subjects.yaml
│   ├── ldap-ca.pem      # корневой сертификат CA домена
│   └── tls/             # в .gitignore
│       ├── server.crt   # копия — на хостинг сайта (FS_LMS_AD_SERVER_CERT)
│       └── server.key   # никогда не покидает сервер; владелец uid 1000
└── data/                # монтируется как /data: state.db и файловые логи
```

На что обратить внимание при разворачивании:

- **Файл окружения должен называться `.env`.** Compose читает его через `env_file`; конфиг,
  перенесённый под другим именем (например `adsync.env`), подхвачен не будет.
- **`config/ldap-ca.pem` обязателен** — без сертификата CA домена LDAPS-соединение не поднимется и
  сервис не стартует.
- **`extra_hosts`** в `docker-compose.yml` резолвит имя DC (`dc.fs.loc`) изнутри контейнера — при
  переезде на другой домен этот маппинг нужно поправить вместе с `LDAP_HOST`.
- **Сеть:** внутрь — `PUBLIC_PORT` (8443) от сайта через проброс на роутере, только с IP сайта;
  наружу — TCP 636 до домен-контроллера. Локальный API (`API_PORT`, 8091) на роутер не пробрасывать.
- **`config/tls/` обязателен** — без сертификата публичный API не поднимется и сервис не стартует.
- **Права на `./data`:** процесс в контейнере работает под непривилегированным `appuser`
  (uid/gid 1000), каталог должен быть ему доступен на запись.
- **После правки `.env`** нужен именно `docker compose up -d --force-recreate` — при простом
  рестарте переменные окружения не перечитываются.

Healthcheck (задан в `docker-compose.yml`) дёргает `/health` изнутри контейнера. Логи, помимо файла, можно направить в Loki через `LOKI_URL`.
